RFC 6455 · WebSocket Handshake

Tại sao WebSocket cần bước hash trong handshake?

Demo tương tác: mô phỏng Sec-WebSocket-Key → SHA-1 → Base64 → Sec-WebSocket-Accept, và chứng minh tại sao bước này ngăn được proxy cache trả lại response cũ.

Vấn đề

Không có hash — dễ bị proxy/cache lừa

Không có hash (unsafe)
Client gửi GET /chat Upgrade: websocket

Proxy cache nhầm trả 101 Switching Protocols từ request trước đó.

Client không thể phân biệt — không có gì để so sánh. Cứ nhận 101 là tin. Kết nối bị "bắt tay hụt".
Có hash — RFC 6455
Client gửi kèm Sec-WebSocket-Key ngẫu nhiên mỗi lần.

Server phải tính hash từ đúng key đó và trả về Sec-WebSocket-Accept.

Client tự tính lại và so sánh — proxy không thể giả mạo vì key mỗi lần khác nhau → hash khác nhau.

Client tạo key ngẫu nhiên

bước tiếp
2
Server ghép key + Magic String (RFC 6455 §1.3)
concat = dGhlIHNhbXBsZSBub25jZQ==258EAFA5-E914-47DA-95CA-C5AB0DC85B11 sha1 = SHA1( concat ) accept = base64( sha1 )
bước tiếp
3
Server gửi response với giá trị đã tính
HTTP/1.1 101 Switching Protocols Upgrade: websocket Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
bước tiếp
4
Client tự tính lại và so sánh
expected = base64(SHA1(key + MAGIC)) = s3pPLMBiTxaQ9kYGzzhZRbK+xOo= received = s3pPLMBiTxaQ9kYGzzhZRbK+xOo= match? → ✓ YES — Handshake hợp lệ!

Magic String  258EAFA5-E914-47DA-95CA-C5AB0DC85B11  là UUID cố định được ghi trong RFC 6455 §1.3 — không có ý nghĩa đặc biệt ngoài việc làm định danh protocol duy nhất. Cả client và server đều hardcode giá trị này.

Mục đích của bước hash — một câu

Bước hash đảm bảo response 101 Switching Protocols mà client nhận được là do chính server này vừa xử lý đúng request này — không phải response cũ/nhầm từ proxy cache — vì mỗi lần connect client tạo key random mới, server phải hash đúng key đó mới match được; proxy không thể tái sử dụng response cũ.
